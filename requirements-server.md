# Server Mode — Requirements

## 1. Goal

Add a persistent server (daemon) mode to nexdb so that multiple tools and processes can query the same database concurrently without each one opening the file from scratch.

## 2. High-level design

```
┌─────────┐   ┌─────────┐   ┌─────────┐
│ client  │   │ client  │   │ client  │  ...
│ (psql)  │   │ (curl)  │   │ (nexdb  │
│         │   │         │   │  shell) │
└────┬────┘   └────┬────┘   └────┬────┘
     │             │             │
     └──────┬──────┴──────┬──────┘
            │             │
     ┌──────┴──────┐ ┌───┴────────┐
     │ TCP socket  │ │ Unix socket│
     └──────┬──────┘ └──────┬─────┘
            │               │
     ┌──────┴───────────────┴──────┐
     │       nexdb daemon          │
     │  (single process,多个线程) │
     │  ┌──────────────────────┐   │
     │  │ connection manager   │   │
     │  │ session state        │   │
     │  │ statement queue      │   │
     │  │ memory/links cache   │   │
     │  └──────────────────────┘   │
     └──────────┬──────────────────┘
                │
         ┌──────┴──────┐
         │ .ndb file   │
         └─────────────┘
```

## 3. Modes of operation

| Flag | Description |
|------|-------------|
| `nexdb serve <path>` | Start daemon, listen on default port (e.g. 7890) |
| `nexdb serve <path> --port 7890` | Custom port |
| `nexdb serve <path> --unix /tmp/nexdb.sock` | Unix socket instead of TCP |
| `nexdb serve <path> --tls` | TLS on TCP (requires cert) |
| `nexdb <path>` | Existing single-user mode unchanged |

Existing CLI flags (`-c`, `-f`, `-r`) continue to work unchanged.

## 4. Wire protocol — two options

### 4a. Simple JSON-over-TCP (recommended for v1)

Most pragmatic first version. Easy to debug, language-agnostic, works with any tool.

**Request** (newline-delimited JSON):
```json
{"sql": "SELECT * FROM t WHERE id = ?", "params": [42], "session": "abc123"}
```

**Response** (newline-delimited JSON):
```json
{"ok": true, "rows": [{"id": 1, "name": "alice"}], "row_count": 1, "columns": ["id","name"]}
{"ok": false, "error": "syntax error at line 1"}
```

Advantages:
- Any language can connect via plain TCP or Unix socket
- Easy to test with `nc` / `socat` / `curl`
- No binary protocol parser to maintain

Disadvantages:
- JSON parsing adds overhead per query
- Large result sets have serialisation cost
- No streaming for big results

### 4b. PostgreSQL wire protocol (nice-to-have)

Enables use of existing `psql` clients, PG drivers, and tooling. Significantly more work.

**Minimum viable subset of PG protocol required:**
- Startup message + authentication (trust or password)
- Simple query (`Q`) message
- RowDescription + DataRow response
- CommandComplete + ReadyForQuery
- Terminate (`X`)
- ErrorResponse on failures

Non-goals for v1: extended query, prepared statements, COPY, SSL, notifications.

### Recommendation

Start with JSON-over-TCP (4a). It gets something working quickly. A PG-protocol adapter can be added later as a separate listener.

## 5. Concurrency model

### 5a. Single-threaded with statement queue (v1)

```
           ┌──────────────┐
client 1───┤              │
client 2───┤  FIFO queue  ├──▶ executor thread
client 3───┤              │    (owns DB handle)
           └──────────────┘
```

- One worker thread owns the `DB` handle and runs all statements
- Client connections are accepted by a separate I/O thread (or event loop)
- Statements are enqueued, executed sequentially, results sent back
- No concurrent file access — sidesteps the existing `flock` limitation
- Simple, correct, good enough for a personal knowledge base

**Blocking concern:** a long-running SELECT blocks all other clients. Mitigation: clients can set a timeout on their request.

### 5b. Multi-threaded read / single-writer (future)

- Multiple reader threads can execute SELECTs in parallel on a read-only snapshot
- Writes queue behind a write lock
- Requires copy-on-write or MVCC in the pager — significant engine change

Not recommended for v1.

## 6. Session state

A session is identified by an opaque token (e.g. UUID) sent by the client with each request. The server holds:

| Field | Notes |
|-------|-------|
| `session_id` | UUID, generated by server on `{"cmd":"connect"}` or first request without one |
| `created` | Timestamp |
| `last_active` | Timestamp, bumped per request |
| `txn_active` | Whether this session has an open `BEGIN` |
| `txn_undo_depth` | Number of undo pages captured in the active txn |

Transactions are **per-session**: `BEGIN` in session A does not affect session B.

Sessions that are idle for > `--session-ttl` (default 5 min) are reaped.

## 7. Authentication (v1)

| Method | Flag | Description |
|--------|------|-------------|
| None | default | Anyone who can connect can run SQL |
| Token | `--token "mypassword"` | Client must send `"token":"mypassword"` in every request |
| Token file | `--token-file /path/to/token` | Read token from file (avoids leaking in `ps`) |

For v1 this is enough. For v2, TLS client certificates or SASL.

## 8. Daemon lifecycle

| Action | Behaviour |
|--------|-----------|
| `nexdb serve` | Forks, opens DB, acquires lock, starts listening |
| SIGTERM / SIGINT | Graceful shutdown: stop accepting, drain queue, checkpoint WAL, close DB, exit |
| SIGHUP | Reopen/reload token file, log rotation |
| Crash | OS closes the file lock; next startup recovers from WAL |

## 9. Command-line interface changes

```
nexdb serve <path> [options]

Options:
  --port N              TCP port (default 7890)
  --unix PATH           Unix socket path (default: none)
  --bind ADDR           Bind address (default 127.0.0.1)
  --tls-cert FILE       TLS certificate (implies --tls)
  --tls-key FILE        TLS private key
  --token STR           Authentication token
  --token-file PATH     Read token from file
  --session-ttl SECS    Idle session timeout (default 300)
  --max-conn N          Max concurrent connections (default 64)
  --daemon              Fork into background
  --pidfile PATH        Write PID file
  --log FILE            Log file (default stderr)
```

## 10. Existing client changes

The nexdb shell (interactive mode) should optionally connect as a client:

```
nexdb --connect localhost:7890
nexdb --connect /tmp/nexdb.sock
```

When connected, it behaves like the existing REPL but sends SQL over the wire instead of calling `exec_stmt` directly.

## 11. Backward compatibility

- Existing single-user mode unchanged.
- File format unchanged — the daemon uses the same `db_open`/`pager_write` paths.
- The WAL works the same way: the daemon is just a long-running process that does `db_close`/`db_open` normally.
- The `flock` in `db_open` prevents two daemon processes from opening the same file.

## 12. Non-goals for v1

- [ ] PostgreSQL wire protocol compatibility
- [ ] Read replicas / replication
- [ ] Sharding / distributed queries
- [ ] Built-in HTTP/REST interface
- [ ] Role-based access control
- [ ] Prepared statement caching
- [ ] Streaming result sets
- [ ] Query cancellation (mid-execution)
- [ ] Load balancing
